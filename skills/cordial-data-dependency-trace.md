# Data Dependency Trace

Localize where a contact attribute's data dependency broke by walking the chain backward: **attribute -> data automation (job) that writes it -> supplement/table it sources -> import feed/batch**, flagging the first layer that is unhealthy.

> Shared mechanics live in the project-root `_reference/` folder (sibling to `recipes/`, i.e. `reference/` from this file): query grammar + the silent-zero and progressive-exclusion traps in `audience-query-mechanics.md`; tool-traversal patterns (and the suspicious-result law) in `tool-ergonomics.md`. **Open and read the referenced `reference/` files before building any query — they are required, not optional (do not work from the SKILL body alone).** This recipe only adds the trace specific to this outcome.

## Steps (the linked path)

1. **Orient** — `whoami` to confirm the account. (Numeric accountID is not in `whoami`; it surfaces later inside batch IDs and schedule data.)
2. **Inspect the attribute — resolve-or-stop first.** `describe_contact_schema` -> find the attribute's `key`, `type`, and `validators`. **If the user's token is NOT in the schema, STOP — resolution failure, not a trace.** Before tracing anything: (a) surface fuzzy near-matches on name AND key (e.g. `store_number` → `home_store`, `last_purch_store`, `closest_store_*`); (b) check whether the token is actually a **supplement COLUMN** (`list_supplements` + a record spot-check — the name may live in a data table, not on the contact); (c) prefer the near-match that live audiences actually target (`search_audience_examples`) as the default candidate; (d) say which surface the user probably saw the value on and trace THAT, labeled as a near-match — never trace an invented key. Report **both** the lexically-targeted candidate and any semantically-strong match (e.g. a store number embedded in supplement string columns) — don't let the live-audience preference crown one alone. **Fully-absent terminal:** if the token is in NO schema attribute and NO supplement column, the user most likely saw it in an external surface (their DWH/BI, a renamed export column) — size only the top candidate cohort, state the external-surface hypothesis, and ask which screen/export showed it. **Handoff key: attribute `key`.** Once resolved, check the validators *first*: if `min >= 1`, then 0 is out-of-range and genuinely broken; if `min: 0`, then 0 may be legitimate — don't call it broken. **Validators settle this only for numbers** — on a *string* field `min` is length, so the by-design-vs-broken call needs a value-shape probe: enumerate the distribution; a decaying integer ladder (0,1,2,3…) is a recency/counter field where `0` is healthy. Distinguish truly-unset (`is_empty`) from a real bad value (`0` / `""`) — different cohorts. Also: no API exposes historical attribute snapshots, so the "suddenly" in the claim is untestable — state that limit rather than implying you verified a change over time.
3. **Quantify the breakage** — first learn this account's wrapper/operator grammar from `search_audience_examples` / `get_account_audience_samples` *before* sizing (the wrapper is account-specific: numeric fields commonly use `{"icfn":{"<key>":{"operator":"...","value":"0"}}}` with operators like `has_value`/`has_no_value`/`gt`/`eq`; a guessed wrapper like `contactAttributeValue` silently returns 0). Then size the bad cohort with `estimate_audience` on the universal base `{"and": [], "exclude": {"or": [...]}}` (progressive exclusion to a deterministic residual; see mechanics). Report the `is_empty` slice and the `=0`/bad-value slice **separately** — and note that **for `min: 1` numerics the real break is almost always `is_empty`, not a literal `0`** (often no `=0` records exist at all), so size both and never assume the 0. **Handoff: bad-value count.** Fire one known-good control query first — a silent zero means "re-check operator/value," not "nothing broke."
4. **Discover the writer (data job)** — `list_data_automations`, querying by **both** the attribute key-prefix (e.g. for a key like `store_region_code`, query `"store"`) **and** the friendly label (e.g. `"region"`); the named writer often surfaces only under the human label, not the attribute prefix. **An empty automations result does NOT mean "no writer"** — the authoritative writer may be a file-import batch (step 6), so don't stop here. **Third writer outcome — REST-API-written (confirmed live):** when NO automation and NO import batch maps the attribute and the batch list is only exports + vendor AI refreshes, the writer is the client's API integration — outside MCP visibility entirely. Name it as such ("writer is API-side; no in-platform job to inspect") rather than reporting "no writer found." Match by `name` / `tags` / and, in `get_data_automation`, the `filterTranslated` referencing the attribute or its supplement. **Handoff key: automation `id`.** `get_data_automation(id)` gives trigger `filter` + `filterTranslated`, `scheduleData.translatedString` (human-readable cron), and `status` — use these to spot a changed schedule/filter **or a disabled writer**. **Honest limit:** for *recurring* automations `get_data_automation` exposes the trigger/filter + schedule but **NOT the inner transformation script**, so usage/cause is attributable at *job level only* (name/key/tags/trigger-filter); report the transform step as an explicit **unidentified slice** and never infer the logic. **But one-time import batches frequently DO leak the inner script** (`get_data_batch` → `transform.dataTransform`) — check them in step 6 to *upgrade* an inferred link to confirmed. Note: `totalRuns` is unreliable (often 0) — use `lastRunAt`/`nextRunAt`/`status` for recency.
5. **Discover the source table (supplement)** — `list_supplements` (prefer over `get_account_supplements`, which has been flaky on `-32000`; retry on connection-lost). Identify the supplement the job reads/writes; `lastRecordModified` (from `list_supplements`) flags staleness — **but `get_supplement.lastDataUpdate` is a DIFFERENT, older date (schema-update, not record freshness; confirmed live with a 6-month divergence)** — read freshness from the list endpoint, never the detail endpoint. **Handoff key: supplement `key`.** `get_supplement(key)` + `list_supplement_records(key)` to spot-check the actual 0/blank values *in the table itself*. Two traps here: (a) **confirm the attribute's column actually exists in the records** — the newest-*named* supplement may not hold the column at all (records expose fields beyond the declared `indexes`, and a same-family older table may be the real source); never claim a supplement is the source on name/index match alone. (b) **`contactLinked: false` is not a dead end** — a reference/lookup table (keyed by zip, store, etc.) is read *by the transform* and written to the contact via `updateContact`, so it can still be the source even though it doesn't join to contacts. **There is no job->supplement->feed foreign key** — the job-to-supplement link is inferred from `tags[]`/`name`/`filterTranslated`. State it as **inferred-from-signals** whenever it isn't confirmed in the trigger filter. **Check the supplement's `description` field first, though** — it sometimes names its writer job explicitly (verified live: an `accountsoldprocessed` supplement described as *"Output from the 'Process Account Sold Data' data job…"*, which `list_data_automations(query="Account Sold")` then resolves directly). A naming match in `description` is a far stronger lineage signal than tag/name inference — promote it to near-confirmed when present. **Supplement layer may be N/A entirely:** for a direct contact-attribute file import there is no supplement in the chain (`list_supplements` returns nothing relevant) — the batch's `dataMapping` (step 6) is then the authoritative feed->attribute join.
6. **Trace the feed (import batch)** — `list_data_batches` (filter by `query` on name/tag; the full list is large and dominated by daily refresh jobs). **Handoff key: batch `id`** (composite format `<accountID>:<24-hex>:ot` — pass the whole string). `get_data_batch(id)` -> `stats{processed,inserted,updated,failures,errors}` for the most recent import's health, plus `transform.dataMapping.mapping[]` — the **only place the feed-column -> contact-attribute join is explicit** (positional array aligned to source columns; `null` = unmapped). Three guardrails before you blame a batch:
   - **Confirm the attribute key is actually IN `mapping[]`.** Similarly-named batches in one series map *different* attributes — a high-failure "full account refresh" batch may not map the target field at all, while only the narrower "field X update" batch does. Never attribute a batch's failures to the attribute unless its key appears in `mapping[]`.
   - **Distinguish import from export.** Check `transform.dataMappingExport` / `dataDestination`: an outbound export (e.g. dest = AWS, `dataMappingExport: "export"`) often shows `0` rows and is NOT the import feed — don't read its stats as the import's health.
   - **Recurring import feeds do not expose `dataMapping`**, so the feed->attribute mapping is often unconfirmable — state it as a limit, don't infer. By contrast, **one-time batches frequently leak the full inner Smarty in `transform.dataTransform`** — read it to upgrade an inferred lineage to confirmed.
   `failures > 0` / a stale `endTime` / a short `processed` count flags the break point. (`transform.testRecord` is a sample mapped row — verify the mapping produced real values without querying contacts.)
7. **Localize** — report the single layer where the chain breaks: **feed batch failed/stale/short** | **supplement values bad/missing-column** | **data job filter/schedule changed OR writer disabled** | **upstream input coverage gap** (the writer is healthy but only writes where its input resolves) | **attribute mapping** — plus the explicit unidentified slice for the inner-script gap. **"No failed batch" ≠ "fresh":** a feed can be healthy (low failures) yet the value stale because the recurring refresher is *disabled* or the last credit-bearing file is months old — distinguish a *failed* feed from a *stale* value.

## Output

A backward trace ending in a localized verdict: the attribute (key, type, validators), the bad-cohort sizing (`is_empty` vs bad-value, separately), the writer job (id/name/tags/trigger-filter/schedule), the inferred source supplement (key, staleness, spot-checked values), and the most-recent feed batch (id, status, stats, feed->attribute mapping). Conclude with the broken layer and an explicit "transform-script step: unidentified (not exposed by the API)" slice. All counts are estimates; the job->supplement linkage is inferred-from-signals unless confirmed in the trigger filter.

## Guardrails

- **Read-only.** Never refresh a batch, re-run a job, or imply any import was triggered or fixed.
- Check `validators` before calling a `0` broken — `min: 0` means 0 can be legitimate. Report `is_empty` and bad-value as distinct cohorts.
- **Silent zero:** an invalid operator or wrong value returns `count: 0` with no error — fire a known-good control before reporting "nothing broke." A bare top-level `exclude` (no `and` base) also silently returns 0; always base it on `{"and": []}`.
- **Job-level only (recurring):** the inner transformation script is not exposed for recurring automations — report it as an unidentified slice. **But one-time batches often leak `transform.dataTransform`** — check them to confirm lineage before settling for "unidentified."
- **Confirm before blaming:** a batch must have the attribute key in `mapping[]` (not just a similar name); a supplement must have the column in its actual records (not just a matching name); check `dataMappingExport`/`dataDestination` so you don't read an outbound export as the import.
- **Stale ≠ failed.** A clean recent import doesn't mean the value is current — a disabled refresher or an old source file makes the value stale even with zero failures. Report "stale" and "failed" as distinct verdicts.
- State the job->supplement link as **inferred-from-signals** unless the trigger filter names the supplement.
- If a result looks suspicious (0 / too clean / doesn't reconcile), apply the suspicious-result law (tool-ergonomics) before reporting.

## Worked example (illustrative — fictional values)

A marketer reports `loyalty_tier_code` "went to 0 for everyone."

1. `whoami` -> confirm account.
2. `describe_contact_schema` -> `loyalty_tier_code` `{type: number, validators: {min: 1, max: 50}}`. Because `min: 1`, a 0 is out-of-range — a real break, not legitimate.
3. `estimate_audience` on `{"and": [], "exclude": {"or": [...]}}` -> ~12,000 contacts at `=0`, ~300 truly `is_empty` (reported separately). Control query on a known-good attribute returns a sane number, so the 0s are real, not a silent zero.
4. `list_data_automations` (query "loyalty") -> a job tagged `loyalty_sync` writes the tier; `get_data_automation` -> `filterTranslated: "All contacts"`, schedule "every hour" — no supplement named in the filter, and the inner script that maps tier code is **not exposed** (unidentified slice).
5. `list_supplements` -> a `loyalty_members` table (`contactLinked: true`) is the inferred source (name/tag only). `list_supplement_records` -> the tier column there still holds real values (e.g. 10, 20) — table is healthy.
6. `list_data_batches` (query "loyalty") -> most recent `get_data_batch` shows `stats.failures: 8,421` and `transform.dataMapping.mapping[]` mapping source column `tier` -> `loyalty_tier_code`. The import largely failed.
7. **Localize:** break is at the **feed batch** (failures > 0); the supplement is healthy and the job schedule/filter look normal. Transform-script step: unidentified. Recommend Solutions inspect the failed import (read-only finding — no action taken).

### Query grammar & traps

Account-agnostic *how-to* for any recipe that touches `estimate_audience` / audience criteria. This file is the **mechanism**; the real **values** are always learned live from the account (never hardcode them here).

## The self-learning loop

For any attribute, learn the account before querying it:

1. **Find it** — `describe_contact_schema` (contact attributes: `key` + `type`) or `describe_account_events` (behavioral). The **type drives the wrapper**.
2. **Learn real values + operators** — `search_audience_examples` (natural-language) and/or `get_account_audience_samples`. Read the returned live query JSON and lift the actual values, operator, and wrapper. These examples are the source of truth.
3. **Fallback when examples don't cover it** (common for `crdl_ai_*` and other unused attributes) — probe empirically with `estimate_audience` (see completeness check below).
4. **Size** — `estimate_audience` with the learned attribute + operator + value(s).

## Grammar notes (verify against live examples — these can vary by account)

- **Wrapper by type:** string → `icfs`, number → `icfn`, date → `icfd`, **array → `icfa`**, geo → `geoRange`. Don't put a numeric field under `icfs`. Arrays expose a `has_value` operator (`{"icfa":{"<key>":{"operator":"has_value"}}}`) — use it for "has any value" coverage rather than excluding `is_empty`.
- **Conditions** always nest under `and` / `or`. Negation goes under an `exclude` block — **but `exclude` needs a base to subtract from.** A top-level `exclude` with no `and`/`or` base returns `count: 0` (a silent-zero variant), not the complement. Pair it with a base: `{"and": [ … ], "exclude": { "or": [ … ] }}`.
- **Universal base / file total:** an **empty `and`** — `{"and": []}` — returns the entire contact file count. Use it as the denominator for account-wide coverage and as the base for a deterministic exclusion residual (`{"and": [], "exclude": {"or": […]}}`).
- **"Is set"** = `is_empty` *negated* (there is no `exists` / `set` / `not_empty` operator).
- **Operators seen in the wild:** `matches`, `in`, `gt` / `lt`, `after`, `is_empty`, `has_domain`, `begins_with`. Subscription state via `channels.email.ss matches ["s"|"u"|"n"]`; validity via `isInvalid` / `isNotInvalid`.
- **The canonical subscribed-state clause, written out in full** (the single most-asked clause; both key notations shown because examples display the comma form while `estimate_audience` usually wants dots — if one silent-zeros, flip to the other):
  - As `search_audience_examples` displays it (comma form): `{"channels":{"channels,email,ss":{"operator":"matches","value":["s"]}}}` — this form can silently return 0 through `estimate_audience`.
  - Converted (the form that worked live): `{"and":[{"channels":{"channels.email.ss":{"operator":"matches","value":["s"]}}}]}` — keep the outer `channels` wrapper object, dot only the inner key.
  - "Emailable" is stricter than "subscribed": saved audiences routinely AND `isNotInvalid: email` onto the `ss` clause — state which definition you used; offer the other as a follow-up.
  - Searching for ss grammar: query status wording ("subscription status subscribed opted in"), not "subscribed to email" — the latter semantically matches subscribe-DATE band audiences instead.
- **`search_audience_examples` payloads can be huge** (>100KB on one line at limit 8) — use a small `limit` (≤5) and re-query rather than one broad pull.
- **`saved_audience` clause works in `estimate_audience`** ◐: criteria lifted from an orchestration fork/filter can reference `{"saved_audience":{"id":"…"}}` — that clause can be fed back to `estimate_audience` as-is to size the referenced audience (confirmed live once).
- **Sibling-attribute value donation:** when the target attribute has no audience example, lift candidate values/casing from a *same-domain sibling* that does (a loyalty-status example donates tier-value candidates for a tier-level field; `tracking_AI_*_High` audiences donate lowercase `high` for an unexampled `crdl_ai_*` dim) — then verify via the residual check before reporting.
- **Geo fields** use a dedicated `geoRange` wrapper for radius targeting: `{"geoRange":{"geo_location":{"distance":15,"operator":"within","units":"mi","location":{"postal_code":"78748"}}}}`. Common geo fields: `geo_location`, `auto_locate_geo`. (Store-level targeting is often an `or` of `home_store matches "<store#>"` plus a `geoRange` around the store's ZIP.)
- **Channel-scoped subscribe/unsubscribe date bands** (`subscribedDate` / `unsubscribedDate`): these are **top-level clause keys** carrying a `channel` (e.g. `"email"`), **NOT** `icfd` and **NOT** contact attributes — they will not appear in `describe_contact_schema`. They are the date-windowable source for subscribe/unsubscribe *flow* (no 12-month ceiling). **Two grammar shapes exist and which one works varies by account — learn the live one from `search_audience_examples` before banding:**
  - **Two-clause `after`/`before`, `AND`ed** (one observed working form): a month `[start, nextStart)` = `{"and":[{"subscribedDate":{"operator":"after","channel":"email","value":"2025-01-01"}},{"subscribedDate":{"operator":"before","channel":"email","value":"2025-02-01"}}]}`. (Some accounts band the upper bound via an `exclude` on the next-month clause instead — same `[start,nextStart)` result.)
  - **Single `between` with a `{gte,lt}` value object** (other observed working form): `{"subscribedDate":{"operator":"between","channel":"email","value":{"gte":"2025-01-01","lt":"2025-02-01"}}}`.
  - **Silent-zero traps (all returned `0`, no error):** nested-path shapes (`{"channels":{"email":{"subscribedDate":{...}}}}`), `between` with a date *array* instead of a `{gte,lt}` object, and (on the account where `after`/`before` was the working form) `between` was unsupported entirely. If a band returns 0, fire the universal-base control, then try the *other* grammar shape — don't read it as "no subscribes that month."

## Two traps to always respect

- **Silent zero.** Invalid operators *and* wrong values both return `count: 0` with no error. A zero means "re-check the operator/value against a real example," not "no data." When in doubt, fire one known-good control query first to confirm the tool is returning live numbers.
- **Enumerate values by progressive exclusion (deterministic).** With no distinct-values endpoint, don't sum guessed values additively. Instead peel known values off and measure the exact remainder: estimate against a real base while `exclude`-ing `is_empty` plus every value found so far — `{"and": [], "exclude": { "or": [ {…is_empty}, {…=v1}, {…=v2} ] }}` (the empty `and` base is required; a bare `exclude` returns 0). When the residual hits ~0 you've found them all; while it's large, add one more candidate and re-measure. **Cap the effort** — these are free-form strings and can be high-cardinality, so capture the meaningful buckets + a deterministic "other" remainder rather than enumerating exhaustively.
- **Distinguish "no value" from "unnamed value."** `is_empty` catches truly-unset fields (often a small slice). A large residual that survives excluding `is_empty` *and* all known values is a **real, non-empty value you haven't named yet** — not null. For Cordial AI `*_category` / `*_string` fields this is almost always the **`no <activity>` bucket** (`no engagement`, `no purchase`); probe that and the residual closes to 0. (Observed: `crdl_ai_engagement_momentum` → `no engagement`; `crdl_ai_average_order_value_category` → `no purchase`, residual hit exactly 0.) Report "no value" and any named bucket separately.

## Coverage idioms

- **Has any value (strings/numbers).** If the account supports a direct `has_value` operator on the field (`{"and":[{"icfs":{"<key>":{"operator":"has_value"}}}]}` — confirm it's real via `search_audience_examples`, don't assume), that's the **simplest primary**. Otherwise (and always as the cross-check) use the **arithmetic residual:** `populated = file_total − direct is_empty(missing)` — fire `{"and":[]}` for the file total and `{"and":[{…is_empty}]}` for the missing count, then subtract. The residual is the **most robust** fallback and self-reconciles (missing + populated must equal file total); a direct `has_value` result that does *not* equal `file_total − is_empty` is a silent-zero/grammar smell — re-check.
- **Has any value via complement — use only as a cross-check, and verify it reconciles.** The complement forms (`{"and":[],"exclude":{"or":[{…is_empty}]}}`, a `{"not":[{…is_empty}]}` wrapper, or an `is_not_empty` operator) are **unreliable on some accounts**: they have been observed silently returning `0`, or **echoing the same value as the direct `is_empty` count** (so populated == missing, summing to ~2× the file). Treat any populated query whose result *equals the `is_empty` count* as suspicious-by-definition and fall back to the `file_total − is_empty` arithmetic. Do **not** put `is_empty` as a positive `and`-member to mean "has value" (a non-empty base `{"and":[{…is_empty}]}` was observed returning `0`).
- **`is_empty` itself can be non-functional on strings.** On some accounts `is_empty:true`, `is_empty:false`, and `not(is_empty:true)` all return `0` for a string dim. When `is_empty` returns 0 but you have other evidence the dim is populated (e.g. positive `in [v1,v2,…]` matches), do not report 0 missing — derive coverage from enumerated-value `in` matches and treat `file_total − populated` as the residual. `not` is **not** a reliable set-complement here either: `not(field in [v1,v2,v3])` has been observed returning the *same* count as the positive `in` match, not the complement.
- **Missing:** the `is_empty` clause directly — **when it works** (see above). Cross-check it reconciles against `file_total − populated`.
- **Distribution:** estimate each value (or `in` a set).
- **Within an audience:** `AND` the attribute clause onto the base audience's criteria.

## Content references (for usage scans)

Attributes appear in message/block content as **Smarty tokens**: `{$contact.<attribute_key>}` (e.g. `{$contact.digital_giftcard_pin}`). Supplements and other data use similar `{$...}` vars. Reusable content is pulled in via `{include 'content:<key>'}`. To find where an attribute is already used, fetch content (`get_sculpt_block`, `get_html_include` — prefer the `key` arg, `get_sculpt_template`, `get_message`) and search for `{$contact.<key>}`.

**Where attributes/content get used, by source:**
- Sculpt blocks / templates, HTML includes → `{$contact.<key>}` and `{include 'content:<key>'}` in content (statically searchable).
- Data automations ("data jobs") → strong signal from name/key/tags; `get_data_automation` exposes trigger **filter criteria** (may reference attributes) + schedule, **but not the inner transformation script** — usage is reportable at job level only.
- Supplements → content sometimes sources from a supplement (data table) instead of a contact attribute (`$utils->getSupplementRecords` with a supplement key, rendering `{$row.<col>}`); note this so usage attribution is accurate. Coupons/gift codes especially are often supplement- or month-rotating-include-driven rather than a static literal.

**Dynamic include binding (blockData) — a static scan blind spot.** Reusable content can be pulled in *dynamically*: a sculpt block whose html is `{include "content:{$blockData.<...>.select_block|default:'<fallback>'}"}` (a "select menu of all HTML Content" widget). The **selected** include key is stored per-message in `blockData` and is **NOT** present in the rendered message HTML — `get_message` exposes only the `|default` fallback. So grepping message bodies for `content:<key>` systematically **misses** these dynamic bindings. Treat any message built on such a block as a *possible* consumer of the target, and flag the per-message selection as an API-unexposed (confirmed-unidentifiable) slice rather than counting it absent.

## Etiquette

- All tools read-only — never imply an audience was built or saved.
- Counts are estimates; say so.
- Transient `MCP server connection lost` happens; retry once.
